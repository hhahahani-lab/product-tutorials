# 交互原型设计与修改

先读 [个人工作约定](references/working-rules.md)。

## 执行
1. 确认页面平台、目标任务、来源 PRD/版本和当前基线。优先读现有 Demo；有参考图时按 [参考图拆解与设计约束](references/reference-design-contract.md) 提取布局、配色与组件规范，明确保留和调整范围。沿用已有设计，不将每次改动都当成视觉重做。
   - Yaloka 活动页先读项目 `rules/activity-demo-common.md` 及其关联布局规范；交付前按该文档检查导航、入口、奖励与记录、周期切换及倒计时，避免重复引入用户已纠正的布局。
2. 梳理页面结构、信息优先级、操作路径和业务状态。状态默认优先复用、简洁、合并：布局和可执行操作相同的场景共用一个页面状态，只有确实改变布局或操作时才拆分。校验失败原因、待发和封顶等结果放在对应交互或记录中，不机械拆成整页状态；必要的后台业务状态仍保留。模拟选项用括号简述包含的场景。资料只展示一个状态时，区分可观察内容与需要补充的状态，不能编造产品规则。双人或关系榜单禁止使用 Top1 居中抬高、Top2/3 分列两侧降低的山形 Top3 排版，只采用以下方案：只突出 Top1，其余名次使用列表；所有名次统一使用列表；Top1 独占一排、Top2/3 位于第二排，其余名次使用列表。所有名次统一使用列表时，Top1、Top2、Top3 保持相同列表结构，但必须使用不同于普通名次的特殊底色区分。只有用户明确指定其他布局时才例外。
3. 默认先使用当前环境的对话内交互预览能力展示布局与主要操作，按反馈调整；读取并遵守相应预览技能。布局明确确认后再生成正式交付文件，预览所需临时实现不算正式交付。用户明确要求直接生成或修改 HTML 时按该次指令直接执行，不增加预览确认。已经确认且未变的布局不重复询问。缺少交互预览能力时说明限制并提供可审阅替代方案，不将静态截图冒称交互，也不推断用户已确认。
4. 设计控件时按业务含义判断：可查询字段才进入筛选区，需要用户录入的字段才进入表单；不要机械把所有字段转控件。
5. 已确认布局后生成可运行 HTML；若无既定工程要求，偏好单文件。已有 HTML 修改请求直接局部更新，保留已有功能。明确要求直接生成 HTML 时遵循该次要求。
6. 实现适用的正常、空、加载、失败、待处理、已完成、禁用等状态与操作反馈。演示数据与真实数据区分；模拟操作放在业务页面或弹窗之外，不混入正式产品流程。
7. 用户要原型侧说明时，按现有页面/说明区逐处提供必要替换文本，保持原页面结构；不自动附加布局重做或实现细节。修改规则时对齐字段名、金额、单位、计算示例与 PRD；若尚无文档修改授权，报告需要同步的位置。不得因改样式擅改业务规则。
8. 移动端及其浏览器原型默认采用随设备可视区域变化的满屏容器、固定导航/已有底部区域、正文内部滚动；不写死像素高度，不让 Tab/二级页随内容撑开。新流程、控件改动或用户纠正后，按 [交互路径与原型回归](references/interaction-checks.md) 核对实际可达状态、操作范围与取消/失败恢复。验证主要点击、Tab、弹窗开关与状态切换；按实际检查能力测试窄屏、文本换行、图片比例。多图并排保留原始宽高比，不为了等高拉伸图片。
9. 持久保存交付文件，注明关联 PRD 与本次改动。只有实际运行或检查过的内容才能声明通过。发布或写入 Figma 是独立交付动作，按用户请求调用相应技能。

## 输出
预览阶段以可操作页面为主，说明本轮变化即可。交付阶段提供文件/站点与简短变更说明，标明未覆盖的状态或检查限制。

## 按需辅助

明确需要前端质量检查、响应式/异常状态补强或精修时可用 `impeccable`；明确探索风格或重设计时可用 `design-taste-frontend`。普通字段、文案与交互小改不自动加载两套辅助流程。辅助 Skill 不能覆盖业务规则、现有风格、授权范围和先预览后交付的约定。
